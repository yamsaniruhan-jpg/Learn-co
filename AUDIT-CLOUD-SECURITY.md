# LearnCo application, security and Cloud SQL audit

Scope: current branch based on `7389e85dc6d9c81c821831d0bc4c02cdc8fb2282`. This is an evidence-based audit, not a certification of every feature or the deployed environment. No cloud/database configuration was changed and no live data was deleted. All manual writes used temporary local databases.

## Immediate priorities

### Critical — owner/admin takeover: authorization hardened; account recovery remains

On an empty isolated local database, email/password signup with the configured owner email returned 201 and role `admin` without proving email ownership. That session successfully accessed both the owner mentor-application list and the admin Copilot cache endpoint. An attacker can claim the owner identity when that email is not already registered; exposure depends on the actual deployment's account state and accessible routes. `server/db.ts`, `server/routes/authRoutes.ts`, `server/middleware/authMiddleware.ts`, `server/routes/mentorshipRoutes.ts`, and `src/db/users.ts` all contain email-based elevation or authorization. The mentor workflow test currently assumes the insecure behavior.

**Changed locally:** owner administrator privileges now require a server-verified Google identity and are bound to the resulting session, rather than an email string or a legacy persisted role. Existing password and legacy sessions continue to work as ordinary user sessions but no longer grant owner privileges. Server authorization, returned roles, UI visibility, SQL synchronization and the checked-in Firestore owner rule were updated; regression tests exercise verified and unverified paths. Firebase Admin must be configured and Google sign-in must work for the legitimate owner to regain admin access. Google identity was mocked in tests; the live provider and deployed rules were not verified.

**Still required:** this does not reclaim or invalidate existing owner accounts, passwords or sessions. An attacker who previously claimed the owner's email may still have ordinary access to that local account and its data, even after the verified owner signs in. Review the real account and session history, and explicitly plan recovery and revocation with the owner. No live sessions were revoked and no cloud rules were deployed. Do not treat the deployment as secure until recovery and the remaining critical issues are addressed.

### Critical — tracked account/session database

`.learnco_db.json` is tracked in Git and contains account data, password hashes and bearer sessions. A metadata-only inspection found four users, three password hashes, and five sessions, two of which had future expiry timestamps at the time of the check. Their actual validity in any deployment is unknown; if a deployment loaded the same session records, knowledge of a token may provide access. Never treat a hash or token in Git history as private.

Before this audit's fix, the development server served this file as JSON over HTTP, including via `/@fs/`. The production bundle served the SPA HTML rather than this JSON in the tested setup. Vite now denies the default store, the configured store and their temporary snapshots in the tested paths; it refuses a configured store under `public/`. `.gitignore` now excludes the default filenames, **but does not untrack an already tracked file or remove Git history**. The database was not deleted or modified. Place real data outside all served and built paths, investigate access/history and deployment state, rotate/revoke potentially exposed sessions and reset affected credentials as appropriate, and plan removal from tracking/history with the owner's approval. Treat backups and historical clones as potentially exposed. Do not use the isolated preview for real accounts.

### Critical — URL import SSRF is only partially mitigated

`server/services/documentExtraction.ts` used automatic redirects, so a public URL could cause a request to a private destination before the final URL was checked. Redirects are now followed manually, checked before each hop and limited; mapped IPv4 and additional local IPv6 literals are rejected. Tests confirm a literal private redirect is not contacted.

**Remaining risk:** hostname checks do not resolve and pin DNS addresses to the actual connection. A public-looking hostname that resolves or rebinds to a private address can still reach internal services, and the size limit is applied after response buffering. Do not consider this endpoint SSRF-safe. Restrict untrusted URL imports/egress operationally until a properly tested resolver, public-address policy and connection pinning for every hop are in place; also bound response streaming. These restrictions and any infrastructure changes require owner approval.

## Functionality and billing

- **High:** `routes/subscription.js` cancellation changes the local/Firestore tier but does not call Stripe to cancel the actual subscription; users could continue to be billed. Webhook processing writes Firestore when available, while other entitlement paths also read the local account; check real entitlement consistency, event retry/idempotency and billing lifecycle before charging customers. The raw-body fix alone does not establish end-to-end billing correctness.
- **High:** JSON persistence is process-local and file-backed. Concurrent instances have independent memory and can overwrite one another's snapshot; ephemeral filesystems can lose data on restart/redeploy. Firestore/SQL mirrors are not a demonstrated transactional replacement. Determine the actual durable storage, backup, restore and deployment topology before production use.
- **Medium:** signup/signin distinguishes missing users from wrong passwords, enabling account enumeration; reset links are written to operator logs if no mail provider is configured. Restrict log access and configure a real delivery provider. A per-IP sign-in rate limit was added, but its in-memory counters are not shared across instances and do not prevent distributed attacks. Auth tokens and some third-party settings are stored in browser localStorage and are exposed to a successful XSS.
- **Medium:** the tested development page emitted a Vite client `WebSocket closed without opened` error because dev websocket/HMR is disabled. The tested production browser page had no page errors. Firebase/Firestore external connections were unavailable in this sandbox; client offline/network errors are not evidence of the live deployment's health.
- **Medium:** the app's main navigation is in component state (`src/App.tsx`), rather than a separate URL for each tab. Browser back/deep-link and reload expectations should be reviewed; no routing redesign was made.

## Cloud SQL, PostgreSQL and Firebase

**What the code actually requires:** PostgreSQL is optional. `src/db/index.ts` only treats SQL as configured when all four runtime SQL environment variables exist, and disables it in tests. Auth synchronizes users to SQL asynchronously; mentor applications and mentor profiles use PostgreSQL when configured. When SQL is absent or only partially configured, mentor applications fall back to the local JSON store. Firestore mirrors are conditional and are separate from both local and SQL state. SQL may point to Cloud SQL or another PostgreSQL host; the code alone cannot identify the live instance.

**Observed isolated failures:** with only `SQL_HOST` set, a test signup and mentor application succeeded using local fallback. With all SQL settings pointed at a deliberately unreachable local endpoint, signup succeeded while application submission returned 503. Thus enabling SQL changes availability and removing it can change where data is read/written. SQL-only applications may become inaccessible; decisions/mirrors can diverge. The successful test suite disables SQL and therefore does not test real connections, schema, concurrency, migrations, permissions, or recovery. No checked-in Drizzle migration directory was found; inspect how the live schema is provisioned before any change.

**Transport and credentials:** the runtime pool has no explicit TLS configuration and the Drizzle CLI configuration sets `ssl: false`. This does not prove traffic is unencrypted: a Cloud SQL connector/proxy or private transport could be in use. Verify actual connection path, encryption, least-privilege runtime versus migration accounts, network allowlists, backups and alerts. Avoid putting credentials in reports or client bundles.

**Firebase:** browser code uses Firebase Auth, Firestore and Storage; the server conditionally uses Admin SDK synchronization. Firestore and Storage rule files are present, but neither deployed rules nor IAM were verified. The Admin SDK bypasses client security rules. The checked-in Firestore rules permit authenticated users to create their own mentor catalog entries, and the Storage `public/` path allows writes by any authenticated user; review whether this conflicts with the intended approval and abuse model. The checked-in `isPlatformOwner()` rule now also requires a verified Google provider claim, but it has not been deployed or tested against a live emulator/project. Leaderboard/public profile data are client-writable within bounds, so do not treat them as authoritative. Rules changes were not deployed.

**Can Cloud SQL be disabled?** The application can run without SQL in the tested local configuration, but there is insufficient evidence that the deployed instance is unused or safe to disable. Inspect non-secret runtime configuration, connection/activity metrics, application and other consumers, schema/data inventory, retention, backups, costs and dependency ownership. Plan a reversible migration and verify all reads/writes before requesting approval for any disabling or deletion. No cloud connector, project credentials, billing, live database, IAM, or deployed configuration were available during this audit; costs and current usage are unknown.

## Dependencies, performance and UX

- `npm audit` reported eight advisories: four high in the Firebase/Firestore/gRPC dependency chain and four moderate in Drizzle tooling/esbuild. npm suggested disruptive downgrades; none were applied blindly. Review upstream compatible versions and advisories, then test upgrades.
- Some Firebase dependencies declare Node >=24.12 while the environment and CI use Node 22. Install/build/tests passed with engine warnings; production compatibility remains unverified. Align and test the supported runtime deliberately.
- Production frontend entry is approximately 1.57 MB uncompressed / 447 kB gzip, in addition to lazy/vendor chunks. Measure real loading and interaction performance on mobile; split further only after profiling.
- Dashboard browser checks found clipped navigation before the responsive changes. Afterward the sampled dashboard widths fit, and mobile bottom destinations remained reachable. This is not exhaustive accessibility, cross-browser, localization, keyboard or every-page responsiveness testing.
- Product strengths worth retaining: a single learning workflow combining curriculum, adaptive practice, Socratic assistance, planner, creator tools and mentor access. Reliability, trustworthy progress and verified mentors are more defensible differentiators than feature count.

## Verification and coverage limits

- Clean `npm ci`, TypeScript lint, production build and **193 tests across 23 files** passed after the auth changes. Bun's frozen lockfile-only check passed; a fresh full Bun installation was not performed.
- Dev and built production servers were started with isolated local files. Health, SPA, unauthenticated 401, unknown API 404, signup and session requests were checked. Production browser sign-in and dashboard rendering worked; local production requests did not receive the tracked database content.
- Actual Chromium browser: signup, four onboarding steps, signout, incorrect-password rejection, signin, recovery after a simulated session-verification outage, dashboard, navigation across 22 visible desktop sections, plus a mobile drawer and sampled bottom navigation/profile interactions. Layout measurements covered the dashboard at multiple widths. This was a navigation/render smoke, not a complete exercise of every button, form, feature, device, browser or accessibility state. One mobile selector initially sought `Planner` while its actual short label is `Plan`; no conclusion about that particular click was drawn from that attempt.
- Automated tests cover portions of auth, practice, planner, creator, mentorship, extraction, persistence, billing guards, curriculum, UI rendering and access control. SQL is disabled in test mode. Real Google sign-in, Firebase/Firestore/Storage, paid AI, mail delivery, Stripe checkout/cancellation, production data, live SQL and deployed security rules were not tested.
- The preview is isolated and non-production, not connected to real services, and inherits the open security risks above. No credentials or personal record contents were copied into this report.
