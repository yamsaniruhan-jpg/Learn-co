# Google sign-in troubleshooting

Google's **403 `access_denied` / “Access blocked”** screen is returned by Google before the application can exchange a Firebase ID token. The message alone does not prove which setting is wrong. Check the exact error details and the OAuth client ID on that screen; do not share authorization codes, tokens, passwords, or client secrets.

## For the project owner

1. In Firebase Console, select the project used by the deployed web app. The committed default in `firebase-applet-config.json` names project `robust-virtue-62t1j` and auth domain `robust-virtue-62t1j.firebaseapp.com`; a deployment may use a build-time override. Enable **Authentication → Sign-in method → Google** and configure its support email. Google sign-in must be enabled in the same Firebase project the client uses.
2. In Google Cloud Console, select the corresponding project and inspect **Google Auth Platform → Audience** and the OAuth client used by the Firebase Google provider. If the audience is external and publishing status is **Testing**, add the affected Google account as a test user, save, and retry that same account. This is a temporary testing arrangement, not general public access. For public access, configure branding, audience, domains and scopes appropriately and complete any verification Google requires before publishing to production. An **Internal** audience is limited to the Google Workspace organization; choose an appropriate audience through the owner's approved configuration process. Workspace administrator or account policies can also deny access.
3. In **Firebase Authentication → Settings → Authorized domains**, add the exact host on which users open the app, if it is not already present. This is distinct from the Google OAuth consent audience; an authorized domain alone does not fix a testing-user denial. Only authorize hosts you control. For embedded previews, open the app in a separate browser tab when popups or third-party storage are blocked.
4. For redirect URI errors, check the Google OAuth **web client** used by Firebase against its provider settings and exact authorized redirect URI. With the committed default auth domain, Firebase's handler is `https://robust-virtue-62t1j.firebaseapp.com/__/auth/handler`. An alternate or custom auth domain has its own handler and may need additional Firebase hosting/proxy setup. Do not add arbitrary redirect URIs. The `oAuthClientId` field in the JSON is not directly used by this application; verify the client ID in Firebase's Google provider and Google's error details rather than assuming that field is the active one.
5. After Google/Firebase returns an ID token, `/api/auth/google` independently verifies it using Firebase Admin. Configure server credentials and `FIREBASE_PROJECT_ID` for the **same** project as the web client. A server 503 means Admin is unavailable; a server 401 can indicate an invalid token or project mismatch. Never bypass server verification to work around OAuth errors.

## Deploying client settings

The committed Firebase web configuration is used by default. Vite embeds `VITE_` settings at **build time**. To override the core settings, set `VITE_FIREBASE_API_KEY`, `VITE_FIREBASE_AUTH_DOMAIN`, `VITE_FIREBASE_PROJECT_ID`, and `VITE_FIREBASE_APP_ID` together from the same Firebase web app, then rebuild and redeploy. Incomplete overrides disable Firebase client initialization rather than mixing projects. Optional bucket, sender, measurement and Firestore database overrides are listed in `.env.example`. When the project changes, the old project's optional resources are not reused; the default Firestore database is used unless `VITE_FIRESTORE_DATABASE_ID` is set. Server Admin's `FIRESTORE_DATABASE_ID` must also be configured appropriately for an alternate project.

These are public client identifiers, not secret credentials. Keep service-account JSON and OAuth client secrets exclusively in the deployment's secret manager, not in `VITE_` variables, Git, screenshots, or chat. Switching projects affects authentication identities, Firestore, Storage and existing user data; inventory, test and plan any migration separately before changing production.

## Verification

Use an approved test account and the actual deployed hostname in a normal browser. Confirm that Google permits the account, that Firebase returns a Google-authenticated ID token, and that `/api/auth/google` returns a successful application session. Then sign out and verify that a non-test account is appropriately permitted or denied according to the intended audience. Avoid recording tokens or personal data. Mocked local tests and a successful build do not prove live OAuth configuration; updating repository code does not alter the Firebase or Google Cloud console settings.
