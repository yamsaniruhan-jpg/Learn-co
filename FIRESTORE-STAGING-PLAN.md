# Firestore staging and durable-storage plan

**Status: design and investigation plan only; not a deployment or completed migration.** The owner selected Firestore as the target and a staging-first approach, and selected investigation before incident containment. No project or credentials were supplied; no cloud resources, backups, rules, data, sessions, or production configuration have been changed. The current app still uses its existing process-local JSON store and best-effort mirrors. Do not represent this document as a tested backup or migration.

## Decisions and prerequisites

1. Identify an owner-controlled **staging Firebase project**, isolated from production, and the actual authoritative stores and instance topology. Confirm environment/project IDs, Firebase Auth tenant, Firestore database mode/location, service accounts and allowed APIs through an authorized channel; never paste credentials, access tokens, user data or reset links into chat or Git. Confirm billing, budget alerts and a cleanup/retention owner before creating resources.
2. Inventory existing Firestore collections, clients, indexes, security rules, TTL policies, data volume and dependencies. Distinguish backend user IDs from Firebase UIDs: email equality alone is not proof of ownership. Define a verified account-linking/mapping process before importing or allowing cross-store access. Resolve unknown or conflicting identities manually; never merge them based solely on email.
3. Specify an approved encrypted backup destination outside the repository, access controls, retention, incident/legal hold, restoration owner, recovery point and recovery time objectives. Back up the *authoritative current state*, not an assumed Git snapshot, and test restoration with sanitized synthetic users in a separate environment.
4. Choose a migration window and rollback conditions; coordinate all instances and writers. Decide which historical records are trusted, how to handle client-supplied awards and unknown provenance, and whether other services still rely on direct writes. Configure staging-only synthetic identities, Stripe test mode and disabled or sandboxed email/AI. Production changes require separate approval after reviewed staging evidence.

## Proposed target architecture (not implemented)

- Keep the API as the authority. Use a dedicated namespaced set of server-managed collections; avoid silently reusing current `/users`, `/resources`, `/marketplace`, or other client-written/mirrored collections. Exact schemas, retention and indexes must be finalized after inventory. The Firebase Admin SDK bypasses client rules, so enforce authorization and tenant/account ownership in server code and use least-privilege IAM in addition to rules.
- Store domain records as separately versioned documents, with server-owned immutable identifiers, timestamps and schema versions. Bound document size and array growth; use subcollections or separate indexed documents for attempts, events and messages. Never store a database-sized JSON blob in a Firestore document.
- Keep credentials, password hashes, bearer sessions and reset tokens in a separately designed protected identity/session system, not public profiles or generic client-readable paths. In an incident migration or restore, do not import exposed sessions, reset links or compromised credentials. Provider account recovery and revoked Firebase refresh tokens require their own process; restoring a database alone must not revive access.
- Use Firestore transactions for attempt idempotency keys, answer verification, daily quotas, once-per-question/day XP awards and leaderboard ledger/balance updates; keep side effects out of retried transaction callbacks. Fix the replay policy for timezone changes and use server timestamps. Store a stable unique attempt key and server-generated award record; handle duplicate and simultaneous requests across independent server processes. Do not trust client answer keys, client timestamps or client-written leaderboard totals. Question keys currently reach clients, so this is not an anti-cheat guarantee.
- Model webhook event IDs and subscription state transitions durably, verify signatures, use transactional idempotency/outbox or reconciler for external side effects, and explicitly handle out-of-order events. Define cancellation, refund, reconciliation and customer support operations before enabling checkout. Never mark a Stripe call successful on database failure or assume a Firestore transaction makes external Stripe requests atomic.
- Define marketplace ownership, publication/moderation, enrollment and review invariants with transactions or explicitly reconciled workflows. Paid entitlement must derive from a validated payment event, not a client field. Model consent and revocation for any mentor handoff or other educational-data sharing.
- Implement a repository interface and incremental adapters with schema validation and failure reporting. Keep the legacy store unchanged during staging design. Add indexes, migration versions, duplicate/conflict reports and resumable checkpoints; expose a feature flag that defaults **off**. Never use silent fallback to JSON when Firestore is configured as the authoritative store: fail closed on missing configuration or unavailable durable storage.

## Migration and recovery gate sequence

1. Inventory deployments and consumers, assess the exposed-repository and Creator-question incidents, and record evidence without disclosing personal data. Confirm source-of-truth and authorized migration scope. No production revocation or history rewrite is implied by the decision to investigate.
2. Write emulator-backed and isolated staging tests for identity, document ownership, default-deny rules, public/private data, server-owned fields, real query shapes, pagination, quotas, multi-instance concurrent transactions, retries, transaction contention, idempotency and partial failures. Test unauthorized queries and Admin/IAM separately: the Admin SDK bypasses Firestore Security Rules. Current repository has static rule checks only; this environment lacks Java and a Firebase emulator, and no live staging rules have been tested.
3. Create a synthetic-only staging dataset and backup, run a dry-run migration with no target writes and a redacted aggregate report, then import into a fresh isolated staging target. Verify counts and checksums by data type, version transforms, referential integrity, duplicate handling, conflict quarantine and application behavior. Never print sensitive records. Measure costs, document and index limits, transaction contention and operational alerts.
4. Run isolated backup/restore exercises: destroy only disposable synthetic staging data with explicit owner approval, restore to a separate target, verify records, rules, indexes, monitoring and application behavior. Prove old sessions/reset tokens are absent or invalid and canary identities work. Measure recovery point/time. A plan or synthetic test is not proof of production recovery.
5. Trial a staged cutover with writes paused or a tested change-capture mechanism. Define one authoritative writer, reconcile through a high-water mark, run read comparisons without exposing data, then explicitly switch traffic. Do not rely on best-effort dual writes as a transactional migration. Establish a time-bounded rollback that cannot lose post-cutover writes or reintroduce revoked credentials; if this cannot be demonstrated, stop.
6. Require written owner acceptance of staging results, costs, monitoring, incident response, retention, backup/restore and rollback before a separate production cutover authorization. Keep checkout disabled until billing lifecycle and real integration tests independently pass.

## Repository security findings for staging validation

- Repository `firestore.rules` currently permits public reads of `/resources/{resourceId}` and broad owner writes to `/users/{userId}/{subcollection}/{docId}`. It also allows client marketplace writes with limited field restrictions. Depending on actual deployed rules and document contents, these may expose private resources or allow modification of data other services treat as authoritative. Deployed rules, existing records, query patterns and external consumers are unknown. Do not deploy a speculative policy without inventory and emulator/staging tests; prioritize investigating these rules and restricting server-owned data and private content.
- `storage.rules` in the branch denies client writes to shared public objects; the actual deployed policy and external upload consumers are unverified. Firestore/Storage client rules do not constrain trusted Admin SDK calls.
- The Creator-to-Practice process-global question-bank issue is fixed only on this branch. Investigate whether the vulnerable endpoint ran in any deployment and whether private content was accessed, using authorized logs and minimal aggregate reporting. The historical exposure cannot be inferred from local tests.
