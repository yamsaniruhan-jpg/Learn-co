# LearnCo audit and launch review

**Assessment: promising integrated learning prototype; not ready for an unrestricted public launch.** The product connects source intake, practice, planning, focus and mentorship in a coherent LearnCo identity. Its main weaknesses are trust and operational readiness: potentially exposed stored account data, non-durable/ambiguous persistence, unverified cloud and billing integrations, and progress/content that can appear more authoritative than it is.

Scope: code review, automated tests and local browser/API checks on branch `arena/b3f44adc-learn-co`, based on `51b02700a3c26f9db2e8aa30d670b4d1fb639d84`. The deployed site was inspected only as an anonymous visitor; authenticated production behavior, cloud resources, live data and external services were not accessible. This is not a certification, penetration test, exhaustive page-by-page interaction test, or a claim that every feature works end to end. No live database, cloud resources, credentials, rules, customer records or subscriptions were changed. The tracked `.learnco_db.json` and restored `server/db.ts` were left unchanged as requested.

## Prioritized outstanding issues

### Critical

1. **Tracked account/session database:** GitHub metadata confirms this repository is public, and `.learnco_db.json` is tracked. The default-branch GitHub history includes four commits touching that path; this local checkout is shallow, so it is not a complete ref inventory. The file includes account and session data; actual access, live deployment use and session validity are unknown. With separate owner approval, investigate access and affected accounts, protect and verify backups, revoke potentially exposed sessions and reset affected credentials, and plan untracking/history handling. Removing the current file alone does not remove history or invalidate credentials. No records were deleted or sessions revoked. See `INCIDENT-RESPONSE-PLAN.md` for a proposed, not-yet-authorized execution plan and `AUDIT-CLOUD-SECURITY.md` for historical evidence.

### High

**Creator-generated question exposure:** the earlier Creator-to-Practice endpoint inserted private creator questions into the process-global question bank, where other users or anonymous question searches could retrieve them and submissions could earn bank XP. This branch stops the insertion, but whether the vulnerable code was deployed, whether any private content was accessed, and any historical XP impact are unknown. Investigate deployment and access logs under the incident plan; local tests do not remediate a running deployment or historical exposure.

2. **Billing is not launch-complete:** new production checkout is deliberately blocked and cancellation explicitly returns `CANCELLATION_UNAVAILABLE`; existing subscriptions are not changed or cancelled. Signed entitlement events now return a retryable error if the subscription store is unavailable. Implement and verify real cancellation or a Stripe customer portal, durable customer/subscription mapping, entitlements, webhook ordering/idempotency and retries, refunds and failure handling before re-enabling checkout. Real Stripe was not available.
3. **Persistence/recovery:** the JSON store is process-local, nontransactional across instances and potentially ephemeral. Marketplace enrollment/review fallback is memory-only. Firebase/SQL mirrors are not proven transactional backups. Creator source/resource mutations and practice submissions now explicitly flush through the existing store and pass isolated restart tests, without changing the restored `server/db.ts`. This does not make that store transactional or safe across processes. The owner selected Firestore with staging first; `FIRESTORE-STAGING-PLAN.md` records a proposed migration and recovery design, not an implemented or tested migration. Inventory actual storage and backups, confirm staging details and test recovery and consistency.
4. **Progress and answer integrity:** Direct client XP updates are now rejected; bank answers are graded against server keys with at most one award per question per day, and unknown questions are labeled unverified and earn no server XP. This is partial hardening, not a trusted competition system: bank questions and keys are exposed to clients, timezone changes or multiple instances can weaken replay controls, historical balances may include unverified awards, and other Firestore consumers may still see client-writable metrics until rules are tested and deployed. Use server-issued challenges, trustworthy persistence, reconciliation and abuse review before competitive or high-stakes claims.
5. **Cloud and security controls unverified:** live Google/Firebase authentication, deployed Firestore/Storage rules and IAM, SQL connectivity/migrations, paid AI, email and Stripe were unavailable. Local tests and mocked Admin SDK calls do not establish deployed permissions or correct cloud behavior. Do not disable SQL or delete cloud resources without inventory, backups, a reversible plan and explicit approval.
6. **Educational accuracy and disclosure:** AI/creator paths contain deterministic template fallbacks; newly generated creator template drafts and the `/api/ai/chat` fallback are labeled. Copilot no longer fabricates model answers or unrelated automatic artifacts when unavailable and refunds its same-day doubt reservation; its retrieved material is labeled context rather than verified citations. Automatic Copilot artifact creation is disabled pending a validated implementation. Existing stored drafts may lack provenance labels, other AI and voice-evaluation paths need review, and generated content can be wrong. Require source validation and independent educational review; verify live model behavior. Other fallback paths may still consume quota.
7. **URL import hardening needs independent deployment validation:** local DNS-rebinding/private-address and streaming limits were implemented and tested, but successful real public HTTPS fetching could not be verified: sandbox certificate validation failed. Validate egress controls, DNS/IPv6/redirects, TLS and actual deployment network policy independently; do not disable certificate verification.

### Medium

8. **Marketplace integrity:** the UI now identifies the seeded fallback catalog as illustrative and warns that memory enrollments/reviews are temporary. Firestore enrollment/counter updates and review aggregation remain separate/nontransactional; reviews do not prove participation. Live Firestore transactions, rules and index behavior are unverified. Publishing without Firebase and paid enrollment fail explicitly rather than pretending to succeed.
9. **Creator flow edge cases:** failed generation now refunds the same-day artifact reservation, and the resource viewer identifies the copied link as a workspace address, not a resource share link. Real resource-specific sharing remains unimplemented. Template drafts can consume quota. Creator source/resource changes are explicitly flushed, but local JSON writes still lack multi-instance transactional guarantees and failure responses cannot guarantee rollback.
10. **Offline limitations:** the cached shell works only after service-worker activation/control; after a reload without a network, server session validation returns the user to sign-in. Old unowned offline attempts are retained but not synced automatically. Same-tab sync is coalesced, but cross-tab localStorage writes are not transactional. XP shown offline is provisional.
11. **Dependencies and runtime:** current `npm audit` reports 14 advisories: 4 high, 8 moderate, 2 low. The high chain includes Firestore's pinned gRPC dependency; npm's suggested Firebase downgrade is breaking and not assumed safe. CI and the documented minimum now target Node 24.12+, matching Firebase package engines; local tests/build also passed on Node 24.22.3. Live Firebase compatibility is still unverified. Review advisory reachability and compatible upstream fixes rather than forcing incompatible versions.
12. **Deployment security review:** account enumeration, bearer tokens in localStorage, CORS/CSP allowances and client-writable Firestore records require deployment-specific review. Repository Firestore rules allow public `/resources` reads and broad owner subcollection writes, potentially exposing private material or enabling tampering with data interpreted as authoritative; deployed policy, data and consumers are unknown. Proposed repository Storage rules deny client writes to shared `/public/**` while preserving reads and private owner paths; they have not been deployed or emulator-tested, and unknown external clients may depend on the old policy. Admin SDK operations bypass client rules. Verify actual consumers and deployed policies in staging before deploying changes.

### Low / product polish

13. The production frontend entry is approximately 1.55 MB uncompressed / 444 kB gzip, with a 5.08 MiB precache. Measure real mobile loading and storage costs; do not infer field performance from bundle size alone.
14. Full accessibility, keyboard, contrast, screen-reader and cross-browser audits remain outstanding. Dashboard progress and navigation labels were improved, but not every control was audited.

## Account isolation and transparency follow-up

- Newly recorded local practice attempts and mastery estimates, notifications and arrival-reminder state are separated by account. Switching accounts immediately displays that account's data instead of reusing the previous account's snapshot. Old unscoped attempts, masteries and notifications remain untouched and are not automatically attributed or displayed; an ownership/recovery decision is still needed. These browser records are neither encrypted nor protected from someone with access to the browser profile, are not backed up across devices, and concurrent cross-tab writes remain nontransactional. Offline provisional local mastery is not reconciled if later server grading differs.
- Dashboard and gamification labels now distinguish device-local estimates and activity points from server leaderboard scores. Creator, copilot, calculus and ladder badges no longer unlock based on unrelated XP or generic practice; their event-specific criteria are not yet tracked and they remain locked. The fixed flash-check quiz now discloses that it is a sample and does not update scheduled review intervals. The offline page distinguishes cached shell, open-session queueing, and network-dependent session/question loading.
- Repository-only Storage rules propose denying authenticated clients writes to shared public objects; read access remains public and owner-scoped private uploads are unchanged. Static policy regression test only: Firebase emulator, deployed rules and external clients remain unverified; no cloud rules or data were changed.
- Node 24.22.3 passed the isolated local test suite, typecheck and production build; CI and `.nvmrc` now select Node 24 and `package.json` documents the >=24.12.0 minimum. Both npm and Bun locked installs were exercised locally. This does not verify live services.
- React tests cover local account switching, stale notification setters, legacy preservation and cross-tab practice refresh. A local production Chromium smoke exercised real local sign-in/sign-out for A → B → A using directly seeded practice records, legacy retention and no page errors. It does not establish cross-device persistence or live deployment behavior.

## Practice correctness follow-up

- Practice and copilot now grade known bank questions with shared question-type-aware logic. Multi-select order no longer changes the result, and new online/offline submissions preserve the selected options as arrays, including options containing commas. Legacy comma-joined multi-select submissions are matched against expected choices in any order, with a search cap of eight expected choices; inherently ambiguous historical strings and larger legacy sets cannot always be reconstructed.
- Numerical bank questions use their configured tolerance (or the previous client default of 0.05), reject malformed/nonfinite values, and keep zero tolerance exact. Symbolic numerical keys are matched as normalized text rather than partially parsed. This is not a symbolic mathematics equivalence engine. Unknown/custom questions remain unverified self-checks and cannot earn server practice XP.
- Corrected the gradient-descent bank question `q-cs-grad-03`: two iterations yield 1.92, consistent with the worked solution, not the old key 2.88. Previously recorded attempts and awards were not retrospectively changed. Other bank content has not been comprehensively reviewed for correctness.
- The practice quota's displayed reset now follows the profile timezone and daylight-saving changes instead of the server's timezone. This does not prevent timezone changes from affecting quotas or awards, fix other quota paths, or address multi-instance races.
- Unit, API, React and offline tests cover these grading cases and idempotent retry behavior; the production API was smoke-tested with a reversed multi-select answer and retry. Client-visible bank keys, old unscoped mastery data, and the storage/competition limitations above remain.

## Local XP follow-up

- New activity points are scoped to an account on this device and kept separate from the latest server practice XP. Server refresh, online practice and offline-sync completion update the server component without replacing local points. Delayed results are not applied to a different signed-in account. The dashboard combines the two for its device display; the leaderboard still uses server values only.
- Unscoped legacy `learnco_user_xp` and transaction logs are left in browser storage and are not automatically attributed to any account, so an older local balance may not appear in the new display. Legacy unscoped practice and notification records are likewise retained but not attributed. Safe migration needs an ownership decision. Device-local points are not backed up or synchronized across devices, cross-tab updates are not transactional, and they are not authoritative.
- Current client profile sync no longer writes the device's combined XP/level to Firestore. Existing Firestore fields are not removed or reconciled; live Firebase remains unverified.

## Latest local hardening

- **Copilot privacy:** response cache keys now include a hash of the user, exact model input and retrieved context; tool/artifact responses are excluded. Chat and streaming also reject conversations not owned by the caller, and do not append after a conversation is deleted during generation. Mocked cache tests and local API isolation tests cover these cases; historical leakage and broader authorization remain unassessed. The unchanged legacy database append helper itself does not enforce ownership, so future callers must do so.
- **Learning trust:** Copilot returns an explicit unavailable message instead of a fabricated model answer, code or automatic artifact; quota is refunded for unavailable responses on the same day. References are labeled retrieved context, not verified citations. Historical generated practice is labeled an unverified self-check, and errors allow cautious retry. Corrected a physics answer and clarified biology and optimization assumptions, with version bumps; the full question bank is not independently reviewed.
- **Failure recovery:** offline attempts and online practice submissions are retained/queued unless the server returns a matching, structurally valid acknowledgement; no XP is invented for malformed success responses. Stream errors and premature disconnects are surfaced, and failed source extraction cannot refund a reservation from a previous quota day against current-day usage. These measures do not solve multi-tab, multi-instance or transactional recovery. Sync status is announced for assistive technologies, but accessibility is not comprehensively audited.
- **Confidence check-in:** practice optionally records a confidence choice before submission, only in account-scoped device storage; it is not sent to the server or used for scoring. The practice hub compares counts for bank-checked local attempts and excludes unverified and provisional entries. This is descriptive, not a mastery or probability estimate; repeated questions count again, only the latest 200 local attempts are retained, and offline records remain provisional locally after sync.
- **Creator transfer privacy:** the Creator-to-Practice endpoint no longer inserts private content into the globally searchable server bank or treats imported content as bank-verified. Both creator-quiz import paths validate explicit answer choices and use unverified self-checks that earn no server XP; the separate learning import remains an ephemeral account-scoped server list. Flashcard and worksheet transfers are unavailable until an honest suitable practice format exists, rather than receiving fabricated distractors. Local HTTP tests cover cross-account/anonymous visibility, no verified XP and invalid quizzes; historical exposure is unknown. New device transfers use account-scoped storage and in-flight transfers check the active account and token. Account switches remount the creator and practice views; legacy unscoped transfer data is left untouched and is not automatically attributed. Local storage is still readable by anyone with access to the browser profile and is not a secure vault.
- **Initial loading:** Practice is now a lazy-loaded module; the production entry bundle decreased from 1,582.51 kB / 449.07 kB gzip to 1,554.08 kB / 443.89 kB gzip, while the full PWA precache increased slightly to 5,197.55 KiB. These are bundle-size measurements, not real-world performance results.

## Additional launch-critical follow-up

- **XP and leaderboard:** reject arbitrary client XP increments; bank-backed practice can award once per question per local day, and unknown/generated questions are labeled unverified and earn no server XP. Copilot uses the same check. Practice attempts and retries flush to the configured store before success. The leaderboard now consumes backend results instead of merging client-writable Firestore scores, and period/subject views sum recorded ledger entries rather than fabricating fractions. Older scores are explicitly labeled unverified. **Trade-off:** focus, planner and other client-side activity awards remain device-local and do not contribute to the server leaderboard. New activity points are account-scoped and retained separately when server XP refreshes; clearing browser storage removes them. Old unscoped XP and logs are left untouched, but are not automatically assigned or shown because their account ownership and server/local split are unknown. A complete event system is still needed to support trustworthy cross-device awards for those features.
- **Repository-only Firestore rule changes:** the proposed `firestore.rules` denies client writes to leaderboard scores and protects server-owned subscription/Stripe/role fields in user documents. No rules were deployed and no cloud data was changed. Firebase emulator and production policy compatibility were not verified here; inspect consumers and test in staging before any owner-approved deployment. Previously client-written billing fields and historical data require separate investigation; these changes do not retroactively clean them.
- **Creator persistence:** source deletion and resource editing/deletion explicitly flush before reporting success, tested across isolated process restarts. A process-local queue serializes explicit creator/practice flushes and continues after failures. The legacy JSON store can still race with other writes and across instances; it is not an approved durability architecture. On write failure, the API reports uncertainty rather than guaranteeing rollback.

## Launch-critical follow-up implemented

- **Billing safety:** block new production paid checkout until cancellation and lifecycle reconciliation are complete; ask Stripe to retry entitlement events when the backing subscription store is unavailable. Existing subscriptions were not modified. Mocked Stripe/signature tests pass; live billing remains untested.
- **Known question grading:** both practice and copilot ignore forged client answer keys for questions found in the server bank; practice also uses bank-owned metadata. Additional follow-up now blocks direct client XP and repeated same-day awards, while unknown questions remain self-checked and unverified.
- **Creator durability:** a generated resource and its versions are flushed to the existing configured store before a success response; a subprocess test verifies immediate-restart recovery with an isolated store. Failed generation refunds its same-day artifact quota. This does not turn JSON into a multi-instance database or fix every update/delete path.
- **Accuracy and transparency:** the legacy hard-coded resource generator and fabricated fallback quiz return explicit unavailable errors rather than unrelated questions. Additional generic AI notes/chat are labeled; oral keyword/length scoring is marked as a practice estimate and fabricated per-section scores were removed. The workspace-link control no longer presents itself as a resource-sharing link and reports clipboard failures. Other AI paths and older resources still require provenance review.

## Ten most valuable improvements (partially implemented; completion remains open)

2. Establish an approved durable, consistent data model with tested backup/restore and migrations.
3. Complete Stripe lifecycle and entitlement reconciliation, including real cancellation.
4. Make practice verification, XP and leaderboards server-authoritative and abuse-resistant.
5. Apply consistent AI/template provenance and source citations; evaluate factual and pedagogical quality.
6. Validate and harden deployed authentication, access rules, secret handling and network egress.
7. Build end-to-end coverage for each major feature, responsive viewport, keyboard path and failure state.
8. Complete offline session, conflict and cross-tab sync design with explicit recovery controls.
9. Make marketplace transactions, paid access, reviews, moderation and course fulfillment trustworthy.
10. Reduce and measure mobile loading costs, improve accessibility, and simplify the path from a learner's goal to their next action.

## Ten innovative educational feature ideas (proposals except where noted)

1. **Evidence-linked learning map:** connect each concept, explanation and practice question to citations in the learner's own sources.
2. **Misconception radar:** identify recurring reasoning errors from worked steps and suggest a targeted corrective exercise.
3. **Confidence calibration (initial implementation):** optional pre-answer confidence and a local descriptive summary of bank-checked results. This does not claim to measure mastery, and further longitudinal evaluation is needed.
4. **Adaptive retrieval planner:** schedule short reviews based on demonstrated recall, workload and forgetting risk rather than time alone.
5. **Simulation-to-proof bridge:** let learners manipulate a simulation, predict an outcome, then relate observations to an equation or proof.
6. **Socratic checkpoint replay:** save pivotal hints and decisions so learners can retrace how they solved a problem without revealing answers too early.
7. **Transfer challenge generator:** revisit a mastered concept in a new real-world context and assess whether understanding transfers.
8. **Explain-back oral coach:** invite a short explanation, compare it to source-backed criteria and clearly label uncertain automated feedback.
9. **Study-plan experiments:** compare two study strategies using opt-in, privacy-preserving personal outcomes rather than generic productivity claims.
10. **Mentor handoff brief:** with learner consent, summarize goals, evidence of progress, misconceptions and questions for a human mentor.

The differentiator is not another isolated chatbot: it is a trustworthy, source-grounded loop connecting creation, practice, simulations, focus and human guidance. These ideas depend on accurate provenance, privacy and verified progress; they should not precede the launch blockers.
